# event-stack

An event-driven backend system using FastAPI and Kafka, PostgreSQL, featuring idempotent consumers, manual offset management, and S3-backed storage for large payloads.

## Tech stack

- FastAPI - API and event producer
- Kafka (KRaft mode) - event streaming
- PostgreSQL - primary datastore and event inbox
- MinIO - S3-compatible object storage (self-hosted alternative to AWS S3)
- Docker and Docker Compose - local orchestration

## Architecture

The system follows a classic event-driven architecture.

Client requests are handled by the FastAPI service, which publishes domain events
(e.g. `orders.created`) to Kafka.  
A separate consumer service processes these events asynchronously.

To ensure reliable processing, the consumer uses an **event inbox pattern** with
manual Kafka offset commits.  
Large event payloads are stored in **MinIO (S3-compatible storage)**, 
while PostgreSQL stores only small payloads, metadata and object references in case of large payloads.
```
Client
  ↓
FastAPI (producer)
  ↓
Kafka topic (orders.created)
  ↓
Consumer
  ├─ store processing state (event_inbox) → PostgreSQL
  └─ store large payloads → MinIO
```

## Idempotency & delivery semantics

Kafka consumption is **at-least-once**: the same message may be delivered more than once
(e.g. after a crash or rebalance).  Processing made safe by combining:

- **Manual offset management**: offsets are committed only after processing succeeds
- **Idempotent consumer** via `event_inbox`: each event is processed only once

### Guarantees (practical)
- **at-least-once**: Kafka delivery 
- **effectively-once per event**: Even if Kafka delivers the same message more than once, the system processes it only once.

### Idempotency strategy

Each event carries a **UUID string (`event_id`)**, generated by the API and included in the Kafka message.
The consumer uses this UUID as the primary idempotency key.

Additionally, the `event_inbox` table enforces a unique constraint on:
- `topic`
- `partition`
- `offset`

This provides protection against:
- duplicate event production
- consumer restarts
- Kafka rebalances and redeliveries
